# Release notes

## v1.2 — Graceful server stop [unreleased]

A server can now be stopped without killing it: `proto_serve_stop()`, called from the application's signal handler, makes `proto_serve` stop accepting, free the port, give the connections in progress a bounded time to finish, and return `PROTO_OK`.

**No breaking changes, but one code moves.** `proto_serve_opts_t` gains a field at the end, so designated initializers and `NULL` keep meaning what they meant, and a server that never calls `proto_serve_stop()` behaves as before — except that the library now holds two descriptors for the life of the process: the channel described below. A key file that does not exist is now `PROTO_E_KEY_NOT_FOUND` (-305) instead of `PROTO_E_KEY_OPEN` (-301), and other causes that code used to cover have codes of their own (see Fixes). Code that tests `rc < 0` sees no difference; code that compares against `PROTO_E_KEY_OPEN` should look at the new codes too. One setup that used to load now fails, on purpose: `auth.pub` given as `enc.key` (see Fixes).

### Graceful stop

Until now `proto_serve` returned only when it could not serve, and the only way to stop a server was to kill it. Measured on a minimal server: `SIGTERM` with no handler killed the process with status 143, and the code after `proto_serve` — closing storage, a last log line, `exit(0)` — never ran. With a handler that set a flag, the process stayed alive and kept accepting connections: the library resumed its wait, and control never came back to look at the flag. A server that handled `SIGTERM` could not be stopped by it at all.

- **`proto_serve_stop()`** asks the running `proto_serve` to stop. It accepts no one else, closes the listening socket — the port is free at once, since the children closed their copy when they were forked — waits for the connections in progress, and returns `PROTO_OK`. The library takes no signal for itself: the application routes the ones it wants (`SIGTERM`, `SIGINT`) to the function from its own handler.
- **`drain_ms`**, a new field in `proto_serve_opts_t`, bounds that wait. `0`, the default, does not wait; a positive value waits up to that many milliseconds and returns as soon as the last child has ended; a negative value fails with `PROTO_E_PARAM` at startup, rather than being read as 0 or as "forever". A connection still open when the time runs out is left running.
- **Safe in a signal handler and on any thread.** The function sets a flag and writes one byte to a socket pair that wakes `proto_serve`, which now waits with `poll()` on the listener and on that pair instead of blocking in `accept()`. The flag is the request, so a stop is never missed between a check and a wait; only the first stop writes, so the pair never fills; `errno` is left as it was found. The pair is created by the first `proto_serve` and never closed in the parent, so a stop called from another thread can never write to a descriptor number that has since been reused for another file. Failing to create it is `PROTO_E_SOCKET`.
- **A stop asked before `proto_serve` starts is kept.** A signal that arrives while the application is still loading keys is no longer swallowed: `proto_serve` sets up, sees it, closes the port and returns `PROTO_OK`. Setting up first is deliberate, so that a port that cannot be opened is still reported.
- **The children are not told — yet.** A child that receives the signal itself (`kill` on its pid, Ctrl-C to the process group, systemd's default `KillMode`) runs the handler it inherited, and there `proto_serve_stop()` ends it at once, as the signal would have without the handler: children behave as they did in v1.1. Ending a child between two messages, with a `BYE` to its client, needs the child to wait on its client and on the stop at the same time — the shape bidirectionality gives it — and is designed in `TODO.md` for v2.0.

Measured on macOS, with `HANDSHAKE_TIMEOUT_MS=2000`: a stop from a signal handler and from another thread returned `PROTO_OK` in 0.30 s, with the port refused afterwards; a stop asked before the first call returned at once, and the next call ran normally; `drain_ms` 5000 returned at 2.10 s, when the last child ended, and `drain_ms` 500 at 0.81 s with the busy child still running; `kill` on one child ended it while the server kept accepting; `SIGTERM` to the server, or to its whole process group, exited 0.

### Fixes

- **Every way of failing to read a key file now says which it was, and none can hang the load.** `proto_load_keys` and `proto_load_pubkey_hex` reported seven different failures to open a file — nothing at the path, a path component that is not a directory, no permission, a symlink loop, a name too long, no descriptors left, a `NULL` path — all as `PROTO_E_KEY_OPEN`, so the message could not say whether to check the path, the permissions or the system. A directory came back as `PROTO_E_KEY_EMPTY` ("key file is empty"), a device such as `/dev/zero` as `PROTO_E_KEY_FORMAT`, and a FIFO with no writer hung the program forever inside `fopen`. The reader now opens with `open()`, refuses anything that is not a regular file before reading a byte — `O_NONBLOCK` keeps a FIFO from hanging the open — and reads with `read()`, so each step has its own `errno`. Four codes are new: `PROTO_E_KEY_NOT_FOUND` (-305) for a path that leads to no file, `PROTO_E_KEY_DENIED` (-306) for a missing permission, `PROTO_E_KEY_NOT_FILE` (-307) for a directory, FIFO or device, and `PROTO_E_KEY_READ` (-308) for a read that fails once the file is open. `PROTO_E_KEY_OPEN` keeps what is left, the system's own shortages, and a `NULL` path is `PROTO_E_PARAM`. Measured case by case on macOS, each failure now gets its own code and the FIFO is refused at once; a failing `read()`, simulated, is `PROTO_E_KEY_READ`, and an interrupted one is retried. Reading without stdio also means the file's contents no longer pass through a buffer that `fclose` frees without wiping.
- **A key file whose line is not just the key says what is around it.** The format stays strict — the key alone on its line, so that a key has one spelling — but every way a line could fail to be that came back as `PROTO_E_KEY_FORMAT`, "not base64 of the expected size", and most of them cannot be seen in an editor: a trailing space, a tab, a byte order mark an editor added, a non-breaking space pasted from a web page. Something around the key is now `PROTO_E_KEY_STRAY` (-309); valid base64 of the wrong size is `PROTO_E_KEY_SIZE` (-310), which is usually the wrong file — `auth.pub` where `auth.key` belongs, or, for the allowlist, the client's secret `auth.key` copied to the server; a blank first line joins the empty file as `PROTO_E_KEY_EMPTY`; and `PROTO_E_KEY_FORMAT` keeps what is genuinely not base64 — a character outside the standard alphabet inside the line, the URL-safe variant, missing padding. Measured on macOS with fourteen malformed files — empty, blank lines, spaces and tabs around the key, a byte order mark, a non-breaking space, quotes, a space inside, the URL-safe variant, missing padding, and a key of each wrong size — each gets the code described here; a failed decode no longer leaves partial key bytes in the caller's buffer, and the decoding buffer is wiped. `enc.key` and `auth.pub` are both 32 bytes, so the size cannot tell those two apart.
- **A loaded key no longer leaves its text behind.** The reader kept the key file's line — the secret key, in base64 — in a buffer on the stack and returned without wiping it, while the same function wiped the seed it derived and the buffer it decoded into. That text could outlive the load in a core dump, in swap, or under a bug elsewhere that reads memory it should not. The buffer is now wiped on every way out of the reader once it holds anything: success, each refusal of the contents, and a read that fails halfway. Checked in a test build that counts the wipes: the line is wiped on success, on `PROTO_E_KEY_EMPTY`, `PROTO_E_KEY_STRAY`, `PROTO_E_KEY_FORMAT` and `PROTO_E_KEY_SIZE`, and on a simulated `EIO`. With the move away from stdio above, loading a key leaves no copy of it behind but the one the caller asked for. The residue itself was not observed on macOS, before or after; the case rests on what the code did.
- **A failed `proto_load_keys` no longer hands back a secret key.** It loads `auth.key` and then `enc.key` into the caller's struct, and when the second failed it returned the error with the first still in place: measured, `out->auth_sk` held the real secret key after the call had reported failure. A caller that sees an error has no reason to wipe keys it believes were never loaded, so the key stayed wherever the struct went. Only a damaged `auth.key` used to be wiped, and only its secret half. Every failure now wipes the whole struct before returning, so an error means there is nothing to clean up — checked for a bad and a missing `enc.key` after a good `auth.key`, a bad and a damaged `auth.key`, and a `NULL` path. A `NULL` `out` is now `PROTO_E_PARAM` rather than a crash.
- **`auth.pub` given as `enc.key` no longer loads.** Both files decode to 32 bytes, and any 32 bytes make an X25519 secret key, so `proto_load_keys` took the public file for the encryption secret and returned `PROTO_OK`; nothing failed after it. But that key is the identity — every `AUTH` line carries it in the clear, and the server keeps it as its allowlist — so anyone who knew the identity could open every message the client sealed: measured, a program holding nothing but `auth.pub` opened what the client had sealed. The key in `auth.pub` is the public key `proto_load_keys` derives from `auth.key`, so the load now compares the two, in constant time, and refuses an encryption key equal to it with the new `PROTO_E_KEY_PUBLIC` (-311), wiping `out` as on any failure. Checked on macOS: that swap gives -311 with `out` wiped; good keys still load, seal and open, and 2000 fresh identities all loaded; the other swaps still give `PROTO_E_KEY_SIZE`. A client that ran this way now stops at the load until it is given a real `enc.key`. What it stored until then was readable by anyone who knew its identity, and the real key cannot open it: to keep it, open each entry with the key in `auth.pub`, passed to `proto_unseal_new` directly, and seal it again. Only the identity's own `auth.pub` can be told this way; key files that say which key they hold and whose, which would catch every swap, are designed for v2.0 in `TODO.md`.
- **`proto_seal` no longer kills the process over a length no message can have.** It computed the sealed size, and that size in base64, before checking the caller's buffer, and both computations wrap. A `msg_len` of `0 - 1` — what `len - 1` gives on an empty string, or the `-1` of a failed `read()` passed on as a length — came out as 47 sealed bytes and 65 base64 characters, passed the buffer check, and reached libsodium, which aborts the process on such a length: measured, `SIGABRT`. A value a little lower would have been written past the buffer instead. A `msg_len` above about 13.8 EB on 64 bits, 3.2 GB on 32, is now `PROTO_E_PARAM`, before anything is computed or allocated, and `proto_seal_new` returns `NULL`. The bound stays under libsodium's own limit and refuses nothing a real message could be: a 16 MB message still seals and opens identical. The same class as the two aborts v1.1 turned into return values.
- **The trust model claimed more than the protocol gives.** It said that only whoever holds `auth.key` could delete or overwrite, that a compromised server loses availability and metadata but not contents, and that a tunnel matters for metadata. Reading is protected, as it said; changing is not. An attacker in the middle of the connection can relay the handshake and act as the user for a session without `auth.key`, since the server is not authenticated to the client; and the server can add entries that decrypt as genuine, since sealed boxes are anonymous and `REGISTER` hands it `enc_pk`. `architecture.md` and the FAQ now say what is protected and what is not, and recommend a tunnel wherever the network is not trusted. The protocol fixes — a protected channel and entries signed by the client — are designed for v2.0 in `TODO.md`.

Documentation: `docs.md` gains a `proto_serve_stop` entry and a "One per process" note, `drain_ms` in the options table, `PROTO_OK` in what `proto_serve` returns, and a worked server that stops on `SIGTERM`; its error tables gain the seven key file codes, its key file format section what the strict format refuses and how, and the `auth.pub` it refuses as `enc.key`, and its FAQ an entry for `PROTO_E_KEY_DENIED`. `architecture.md` explains the four choices behind the stop; `TODO.md` keeps the child half, for v2.0.

## v1.1 — Error codes, keepalive and fixes [2026-10-13]

Four things: every `int`-returning function now returns a named reason instead of `-1`, connections can opt into TCP keepalive, a server can choose which interface to listen on, and eighteen defects carried over from v1.0 are fixed.

**Two breaking changes for consuming projects.** Add `status.c` to the source list, and pass a fifth argument to `proto_serve` — `NULL` keeps the old behaviour. Everything else compiles and behaves the same, because every error code is negative and the old `rc < 0` / `rc != 0` tests still hold.

### Error codes

New module `status` — the `proto_status_t` enum (37 values) and `proto_strerror()`, which turns any of them into a sentence. It is a status type, not an error type: alongside the failures it names the three successes that carry information.

- **`rc < 0` means failure, always.** Failures are negative; success is `0` or positive. `proto_recv_line` returns a line length, `proto_auth_client` returns `PROTO_REGISTER_REQUESTED` when the server wants our encryption key, and `proto_keepalive` returns `PROTO_KEEPALIVE_DEFAULTED` when probing works but a timing knob kept the system value. Adopting the codes costs a recompile, not an audit.
- **The library stopped printing.** `crypto.c` used to write "Error: could not open …" to `stderr`, deciding for every consumer where its diagnostics appeared — useless to a daemon with structured logging or to a GUI. The reason now travels in the return value and the application formats it.
- **A documented pitfall is gone.** `proto_connect` could not distinguish "network down" from "access denied"; `PROTO_E_RESOLVE`, `PROTO_E_CONNECT`, `PROTO_E_REJECTED` and `PROTO_E_REGISTER_REJECTED` now say which stage failed.
- **`bind` failures are classified.** `PROTO_E_PORT_IN_USE` and `PROTO_E_PERM_DENIED` come from reading `errno` before `close()` can clobber it — between them they cover almost every real startup failure.
- **EOF is distinguishable from an error.** `PROTO_E_PEER_CLOSED` for a clean close, `PROTO_E_READ` for a failed read.
- **A damaged key file says so where it is loaded.** `auth.key` holds the Ed25519 seed and a copy of the public key derived from it, and `proto_load_keys` used to trust the copy. A file whose copy was wrong — one base64 character changed while copying it by hand keeps the size right and decodes fine — loaded as success, and the failure surfaced at the server as `PROTO_E_REJECTED`, which sends the user to check the allowlist. The copy is now checked against the key derived from the seed, and a mismatch fails the load with the new `PROTO_E_KEY_MISMATCH` (-304).

Failure values are grouped in hundreds by family — `-1xx` caller mistakes, `-2xx` resources, `-3xx` key files, `-4xx` cryptography, `-5xx` sockets, `-6xx` lines, `-7xx` handshake — sequential within each range and never reused, so the documented tables stay ordered as codes are added. Values are stable from this release on. Every code has a message, and `proto_strerror` answers for unknown values too, so any return value can be passed straight through.

### Keepalive

`wire` grows from four functions to six. `proto_keepalive(fd, idle_s, intvl_s, count)` turns on TCP keepalive probing for a connection and sets its timing; any argument `<= 0` leaves that knob at the system default. `proto_recv_line_timeout(fd, buf, bufsz, ms)` is `proto_recv_line` with a deadline, described under Fixes below, where it earns its place.

A peer that vanishes without closing — a suspended laptop, a phone off the network — sends nothing, so the other side blocks in `read()` indefinitely. On a forking server that leaves a child alive forever, holding a socket and whatever per-connection state the application keeps. Keepalive makes the kernel probe an idle connection and fail the socket when the peer stops answering, which ends the read and lets the existing teardown path run.

- **Nothing is on by default.** `proto_connect` and `proto_serve` set no keepalive; a connection behaves exactly as in v1.0 until an application asks otherwise. One rule for both ends, and no policy imposed on a consumer that did not want it. Clients call it on `conn.fd` after connecting, servers on the handler's fd.
- **The handshake needs no keepalive.** `proto_serve` accepts, forks and authenticates before the application sees the fd, so probing enabled in a handler starts after the handshake. That window is bounded by the handshake timeout instead (see Fixes), whether the peer vanished or merely went quiet.
- **The platform difference lives in the library.** The first knob is spelled `TCP_KEEPIDLE` on Linux and `TCP_KEEPALIVE` on macOS; `proto_keepalive` absorbs that `#ifdef` so consumers do not repeat it. The other two (`TCP_KEEPINTVL`, `TCP_KEEPCNT`) are spelled the same everywhere.
- **Not a read timeout.** It does not touch read semantics: no `SO_RCVTIMEO`, no partial-line hazard. Detection takes about two hours at system defaults — a backstop against blocking forever, not a way to give up promptly.
- **The kernel handles both sides.** Probes are answered by the peer's TCP stack, so no application, on either end, needs to know or be updated. Nothing is added to the wire protocol: a v1.0 peer interoperates unchanged.

### Bind address

`proto_serve` takes a fifth parameter, `const proto_serve_opts_t *opts`, and the struct has one field: `bind_addr`, an IPv4 literal to listen on. `NULL` — for the struct or the field — listens on every interface, as v1.0 did. A malformed address fails with `PROTO_E_BAD_ADDRESS` before the port is bound, alongside the other caller mistakes.

- **A struct, not a string,** so later deployment options join it without another signature change. Zero means default, so a designated initializer naming one field is complete: `{ .bind_addr = "127.0.0.1" }`. Never pass an uninitialized struct.
- **Deployment options only.** The timeouts are not in it: they are per-project policy and come from `-D` in the consuming Makefile (see Fixes).
- **No name resolution.** A bind address is a fact about the host; what a name resolves to at startup is not one.

### Fixes

- **Out-of-bounds write in `proto_recv_line`.** `bufsz` is a `size_t`, so the loop bound `bufsz - 1` underflowed to `SIZE_MAX` when a caller passed `0`, and the function wrote incoming bytes into a buffer with no capacity. It now rejects `bufsz == 0` and bounds the loop with `i + 1 < bufsz`, which cannot underflow.
- **Segfault on an unusable allowlist.** `proto_auth_server` ran the whole handshake and then called `strcmp(hex, allowed_hex)` without checking it, so a server configured from an environment variable or a zeroed struct died of `SIGSEGV` in every forked child — silently, since the parent survived and the reaper collected the corpse. `proto_serve` now refuses to start on an allowlist that is `NULL` or not 64 lowercase hex characters, or on a `NULL` handler, before the port is bound; `proto_auth_server` sends `FAIL internal error` and returns `NULL` before reading `HELLO`. Checking the length alone would not do: an allowlist written in uppercase — by another tool, or copied by hand — has the right length and matches no identity, since identities are compared as `sodium_bin2hex` writes them, so the server would start and refuse every client.
- **Two aborts became return values.** `sodium_bin2hex` and `sodium_bin2base64` kill the process when handed an undersized buffer, and `proto_load_pubkey_hex` and `proto_seal` passed caller-supplied sizes straight through. Both now check first and return `PROTO_E_BUFFER_TOO_SMALL`. `docs.md` claimed `proto_seal` returned `-1` in that case; it did not.
- **Silent line truncation.** `proto_recv_line` returned a length whether or not the line fit, so a truncation — which leaves the rest of the line in the socket and desynchronizes every read after it — looked exactly like success. It now returns `PROTO_E_LINE_TOO_LONG`, and NUL-terminates `buf` on every error path.
- **Short writes reported as failures.** `write()` may transfer fewer bytes than asked; `proto_send_line` and `proto_send_prefixed` treated that as an error with part of the line already on the wire, leaving the stream desynchronized. Both now resume until everything is sent, so they either deliver the whole line or fail on a real connection error.
- **Signals aborted reads.** A signal arriving during a blocked `read()` returns `EINTR` with nothing consumed; the library reported it as `PROTO_E_READ` and lost the line that arrived a moment later. Reads and writes now retry on `EINTR`. The consequence — a handler alone cannot cancel a blocked read; `shutdown()` on the fd can — is documented in the FAQ.
- **SIGPIPE killed clients.** Writing to a peer that had closed raised `SIGPIPE`, whose default action terminates the process before `write()` can return, so the `PROTO_E_WRITE` path never ran and a client lost whatever it was doing. `proto_serve` had always ignored the signal process-wide; `proto_connect` never did. The library's writes now use `send()` with `MSG_NOSIGNAL`, per call, so a dead peer surfaces as `PROTO_E_WRITE` on either end without the library deciding the process's signal disposition.
- **Silent peers held server children forever.** Every handshake read blocked with no deadline, so anything that opened a TCP connection and sent nothing — a port scanner, a health check, a client that crashed after `connect()` — left a forked child in `read()` for good, and keepalive cannot help, because a silent peer that is still there answers every probe. Five such connections cost five immortal processes. Each handshake read now runs under `HANDSHAKE_TIMEOUT_MS` (10 s) via the new `proto_recv_line_timeout`, and fails with `PROTO_E_TIMEOUT` when it passes; the child returns and is reaped. The same bound protects a client whose server accepted and went quiet, and `proto_close` waits at most `QUIT_TIMEOUT_MS` (2 s) for `BYE` rather than indefinitely. Both constants are `#ifndef` defaults in `protocol.h`: a consuming project sets its own with `-DHANDSHAKE_TIMEOUT_MS=…` in its Makefile, without editing the library.
- **`keygen` exposed secrets for an instant, and overwrote identities.** It created each key file with `fopen`, which uses the umask default — usually world-readable — wrote the secret, and only then `chmod`ed it to `0600` without checking the result; a full disk went unnoticed too, and a second run silently replaced an identity whose `enc.key` may have had no other copy. Files are now created `0600` in the `open()` itself, with `O_EXCL` so an existing key is refused, and write errors are reported with the partial file removed. On a filesystem that cannot enforce permissions (FAT, some network mounts) the tool detects it before writing anything, warns, and asks; without a terminal the answer is no.
- **Only the first address of a host was ever tried.** `getaddrinfo` returns a list — a name usually has an IPv6 and an IPv4, and resolvers list the IPv6 first — but `proto_connect` connected to the first entry and gave up if it failed. A server listening on `127.0.0.1` was unreachable as `localhost` wherever `::1` comes first, and a client with no IPv6 route never got as far as the IPv4. It now walks the list in the resolver's order and stops at the first address that connects. `PROTO_E_CONNECT` means every address refused; `PROTO_E_SOCKET` means no offered address family exists on this host, and one no longer masks the other.
- **Out-of-range ports were folded, or blamed on the hostname.** `proto_serve` cast the port to 16 bits, so `70000` became `4464` and the server started — without error — on a port no client would look at; `0` asked the kernel for any free port, with the same result. Both are what a missing or mistyped `PORT` variable produces. `proto_connect` handed the number to `getaddrinfo`, which refused it as `PROTO_E_RESOLVE`, sending the caller to check a hostname that was fine. Both entry points now check the range first and return `PROTO_E_BAD_PORT`.
- **Reconnecting leaked the previous socket.** `proto_connect` wrote the new socket over `conn->fd` without looking at what was there, so a client that called it again — after a read reported the peer gone, after a timeout, on a "reconnect" command — lost the number of the old socket. Nothing could close it any more, and on the server the child serving it stayed blocked in `read()` until the client process exited: one descriptor and one server process per attempt. `proto_connect` now closes the connection the conn still holds before opening the new one, as `proto_close` would, so reconnecting is simply calling it again. It closes only what the kernel confirms is a socket: a `{0}`-initialized struct has `fd == 0`, which is stdin, and that is left alone — in `proto_close` too, which used to close it.
- **`accept` and `fork` failures were unhandled.** An `accept` error of any kind was retried at once. Out of descriptors or memory, on Linux the pending connection stays queued and `accept` fails again immediately: a busy loop at full CPU. A listening socket gone bad (`EBADF`, `EINVAL`) failed forever, and since `proto_serve` never returned, the application could not know its server had stopped serving. A failed `fork` fell through to the parent's `close`, hanging up on a client that had just sent `HELLO`; the client saw a read error and blamed the network. Now: transient `accept` errors are retried at once, resource errors after 100 ms, and anything else returns `PROTO_E_ACCEPT`; a failed `fork` answers `FAIL server busy` before closing, and `proto_auth_client` reports a `FAIL` in place of the challenge as `PROTO_E_REJECTED` rather than an unexpected reply — which also covers the `FAIL internal error` the server already sent for an unusable allowlist. `proto_serve` therefore no longer "blocks forever": it returns only when it cannot serve, at startup or later. The handler that collects exited children now leaves `errno` as it found it: it ends with `waitpid` failing with `ECHILD`, and a child exiting between a failed `accept` and the check would have made a shortage of descriptors — the moment children exiting is most likely — look like a broken socket, and stopped the server.
- **Lines were read one byte per system call.** `read(fd, &c, 1)` for every byte, so a 1 MB payload line — a photo — cost a million calls and 1.2 s of CPU. Blocks were avoided because they would pull bytes of the next line out of the socket, and an API on a bare fd has nowhere to keep them. The readers now peek (`MSG_PEEK`) at what the socket holds, find the newline, and consume exactly up to it: nothing buffered, nothing over-read, two calls per chunk instead of one per byte. The same 1 MB line takes 3 ms. The chunk size is a new compile-time option, `READ_CHUNK` (64 KB, `#ifndef`, `-D` from the consuming Makefile, declared in `wire.h` so that module still needs nothing but libc); it bounds each peek, so a short line still costs only its length, and it is worth calibrating only between 64 KB and 256 KB — a peek never returns more than the socket holds. Semantics are unchanged — `\r` dropped, `PROTO_E_LINE_TOO_LONG` leaves the rest in the socket, the per-line deadline holds — and a descriptor that is not a socket falls back to the old byte-at-a-time read.
- **A line could be made to allocate without end.** `proto_recv_line_dyn` doubled its buffer until the newline arrived, and a peer that never sent one — broken, or hostile — made the other side allocate until the system killed it, once per connection on a forking server. Lines are now capped at `MAX_PAYLOAD` (16 MB, a new compile-time option in `wire.h`), past which the read stops with `PROTO_E_LINE_TOO_LONG` and nothing more is allocated. The limit is exact regardless of how the peer's bytes arrive, and it bounds one message, not what an application can transfer: larger transfers are several messages, which also bounds what a dropped connection costs. Because "too big" deserves a different answer from "peer gone", `proto_recv_line_dyn_status(fd, &rc)` reports the reason — `PROTO_E_LINE_TOO_LONG`, `PROTO_E_PEER_CLOSED`, `PROTO_E_READ` or `PROTO_E_NOMEM` — while `proto_recv_line_dyn` keeps its signature and its `NULL`. `proto_strerror(PROTO_E_LINE_TOO_LONG)` now reads "line longer than the limit", since the limit is a caller buffer in one reader and `MAX_PAYLOAD` in the other.
- **A line that exactly filled the buffer was refused.** `proto_recv_line` gave up as soon as the buffer was full, without looking at whether the next character was the newline, so a line of exactly `bufsz - 1` characters — which fits, and which the documented limit promises — came back as `PROTO_E_LINE_TOO_LONG`. The same blind spot misreported a peer that closed at that point as too-long rather than `PROTO_E_PEER_CLOSED`, refused an empty line into a one-byte buffer, and counted a carriage return at the boundary as a character. The reader now takes one more character, on the stack, to tell the two cases apart: a newline ends the line, anything else is genuinely too long. Carried over from v1.0 and found while reviewing the peek rewrite.
- **Connecting had no deadline.** `proto_connect` called `connect()` and waited for whatever the kernel allowed: an address that answers nothing — a firewall dropping packets, a host that is down — cost 75 s here on macOS and about twice that on Linux, once per address the name resolves to. Each attempt now runs on a briefly non-blocking socket under `CONNECT_TIMEOUT_MS` (10 s, a new compile-time option in `protocol.h`), measured at 10.01 s against a silent address where the old code took 75.01 s; the descriptor is blocking again before the handshake, which depends on it. Silence is reported as the new `PROTO_E_CONNECT_TIMEOUT` (-510) rather than `PROTO_E_CONNECT`, because "nobody answered" and "something answered, refusing" send the user to different places — the network or the server. A refusal at any address wins over silence at another, being the more definite fact; a kernel that gives up before the deadline — its own limit is shorter than a generous setting — is silence too, not a refusal. All three timeouts are now range-checked at build time, like `READ_CHUNK` and `MAX_PAYLOAD`: a negative `HANDSHAKE_TIMEOUT_MS` reads as *no deadline* and would have quietly restored the immortal-children defect above.
- **Handlers could not see how the programs they ran ended.** `proto_serve` installs a `SIGCHLD` handler that collects every child that exits, and the forked child running the application's handler inherited it. Whatever that handler started itself — with `popen`, `system` or its own `fork` — was collected by the library the moment it exited, so `pclose` failed with `ECHILD` and `waitpid` never saw a status. Not by chance, but every time: five runs of `popen("exit 3")` inside a handler, five failures. The child now restores the default for `SIGCHLD` right after the fork, and the same five runs return status 3. The parent keeps its reaper, and `SIGPIPE` stays ignored in the child, where it protects the handler's own writes.

Documentation: `docs.md` gains an "Error codes" section, reference entries for `proto_keepalive` and `proto_recv_line_timeout`, a note on overriding the timeouts from a consuming Makefile, and every `Returns` line lists its codes; `architecture.md` documents the new module and why the library does not print.

## v1.0 — Extraction (e33b181) [2026-07-03]

First release of `proto` as a standalone library, extracted from the diary project for reuse: everything identical across projects that share its architecture (authenticated clients, server as encrypted blob store, text-line protocol), and nothing that varies (verbs, storage, policy).

- **Four modules, 17 entry points, strictly layered** (dependencies point downward only): `wire` — line framing (`proto_send_line`, `proto_recv_line`, `proto_recv_line_dyn`, `proto_send_prefixed`); `crypto` — keys and libsodium wrappers (`proto_init`, `proto_load_keys`, `proto_load_pubkey_hex`, `proto_seal`, `proto_seal_new`, `proto_unseal_new`, `proto_sign_challenge`, `proto_verify_challenge`); `auth` — sessions and handshake (`proto_connect`, `proto_close`, `proto_auth_client`, `proto_auth_server`); `serve` — fork-per-connection harness (`proto_serve`).
- **The contract** (`protocol.h`): one message = one `\n`-terminated line; binary travels base64 inside lines; `HELLO → CHALLENGE → AUTH [→ REGISTER]` handshake; `QUIT`/`BYE` teardown; application commands layered on top by each project.
- **Trust model**: Ed25519 challenge-response identity (the public key is the username), X25519 sealed-box payloads the server stores but cannot read. No TLS by design — payload confidentiality comes from the sealed boxes; tunnel if metadata privacy matters.
- **`keygen/`** — bundled, de-branded key provisioning tool writing `auth.key`, `auth.pub`, `enc.key`; lives in the library because the key-file format is part of its contract. X25519 keys generated via `crypto_box_keypair`.
- **Documentation set**: `README.md` (intro), `architecture.md` (design rationale), `docs.md` (complete API reference with worked examples).
